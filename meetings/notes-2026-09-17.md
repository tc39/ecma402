### PR #1074: Allow Locale.p.getNumberingSystems to return >1 item — Consensus on updated text distinguishing supported systems from those in common use.

https://github.com/tc39/ecma402/pull/1074

JMN: (Reads out PFC’s prepared text, PFC is not present to discuss this. His prepared text:)

PFC:  Can we get agreement to merge this with my change to address Anba's comment (second commit), or does it need to go through the consensus process again?

PFC: the change is basically to fix the fact that "supported numbering systems for a locale" and "numbering systems in common use in a locale" are not the same. in the first iteration, I erroneously assumed that they were. ICU "supports" any base-10 numbering system in any locale (e.g. US English with Malayalam digits) but new Intl.Locale('en-US').getNumberingSystems() should not include Malayalam.

SFC: I think this latest revision is fine. We’re changing numbering systems of locale to have this new language. Do we do that in the other ones–the other similar functions? I’m thinking of Collations in particular. For Collator, we just copy found locale data. Whereas now in numbering systems, instead of copying found locale data, we are using additional implementation-defined data to filter that list. I think that’s okay, but it is an extra place where we’re adding additional locale data. That raises the questions: should we do the same for collations? Should we do it for calendars? Calendars does this already. Collations is not common use, it’s just what’s supported in the locale data. And numbering systems is now in common use. We have two different things going on. I’m happy that we have the “in common use” thing going on. We should probably be explicit about the implementation-defined part. Since the pull request is substantially different than the original, I think we should indeed get approval again. But that should be easy since we are all here now and since the TG is meeting in a couple weeks.

SFC: Any objections to this patch? Hearing none, I’m goingt to say that we have TG2 approval for the new version of gh-1074.

#### Conclusion

TG2 approval.

### Sequence Units Issue #14: Significant digit formatting is problematic with sequence units — Erroring on maximumSignificantDigits with non-decimal ratios.

https://github.com/tc39/proposal-intl-sequence-units/issues/14

JMN: The “amounts” proposal throws if significant digits is converted to an option, which is what EAO is suggesting here.

SFC: Separation of concerns between 402 formatting and Amount. Let’s throw an exception, as recommended here.

RGN: +1

SFC: I think minimum significant digits should also fail, contrary to what EAO suggests.

RGN: Agree that it’s equally problematic.

SFC: [missed this bit]

RGN: Presence of option should throw.

SFC: How does this relate to the rounding priority option?

RGN: Probably also throw if rounding priority specifies significant digits. Take a consistent position: significant digits is not applicable to sequence units. Any attempt at application is an error. What are the options?

SFC: auto, more precision, less precision. Auto means: if significant digits option, use it, else use fraction digits. So significant digit could be a possible code path.

RGN: I think then that auto would be the only valid rounding priority.

SFC: Agree. Also can be said as: After the function finishes running, if the max/min option is set, then that’s an error case.

SFC: We have rounding type. Different from rounding priority. Error condition is not fraction digits. That’s the only permissible rounding type. And rounding type is derived from… SetNumberFormatOptions. Very early in the constructor. We can add a check.

RGN: I was interested in seeing where user code runs to check whether we’re doing it early enough.

SFC: We’re getting all the options.

RGN: That’s what I want. It does mean that if you set one of those values, which should be ignored, to something out-of-bounds, then yo’ll get the OOB error rather “not applicable” error. I think that’s fine.

SFC: Exact order of options can be discussed in the PR. Decision for today is: the general condition under which an exception should be thrown. And it sounds like there’s agreement.

RGN: Agree.

JMN: What was wrong with EAO’s intuition about min significant digits being OK (just padding zeros, at most)?

SFC: We're being a bit more strict. A concern I have with allowing minimumSignificantDigits is that we would need to define an algorithm for how to split the significant digits between the units in the sequence unit, which seems like a brittle area we don't need to explore, so we shouldn't eagerly explore it until we have a use case.

#### Conclusion

Throw an exception when the Intl.NumberFormat is configured to use significant digit rounding, which is tracked by the `[[RoundingType]]` slot. The only permissible value of `[[RoundingType]]` should be Fraction Digit rounding. The exact order of operations for when to throw the exception will be discussed in the PR.
