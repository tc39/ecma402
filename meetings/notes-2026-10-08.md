### Time Zone Issue

JGT presents the issue: https://github.com/tc39/ecma402/issues/1103

Time zone IDs such as EST5EDT, etc., were deprecated and now undeprecated because of complaints about compatibility, and are now primary zones in TZDB. This means that now they will be enumerated in Intl.supportedValuesOf and shown in time zone pickers, which may lead to web users choosing the wrong time zones. Most users will not know the pitfalls of these weird zones, such as that they don't match historical or future dates, especially in the face of many jurisdictions in the US and Canada switching away from daylight saving time.

Three things we could do:

1. Consider this an edge case. It will only affect a small percentage of users.
2. Revert the change. We'll discuss the implications of this.
3. Change the behaviour of how enumeration works to improve the UI picker experience.

Specifically about option 2, the TZDB folks will probably be unwilling to revert this and they may have good reasons beyond ECMAScript. CLDR had little enthusiasm to revert it as well, but they may be open to us making a change in ECMAScript. We also already special-case zones such as "UTC".

EAO: Do we know that the effective number of users is nonzero?

JGT: Vast majority are probably Linux. There are non-zero users who use these zones, and I think it’s a safe assumption that they expect the behavior to match that of the standard zones.

EAO: Do you know this from research? I discovered talking to HJS earlier today that these don't work on Safari.

JGT: I did a little research. The main thing I’ve heard is that “I know people who use this.” It is absolutely not a major thing. But across the billions of decides across the web, there is a non-zero set. Probably a lot of them are Linux sysadmins who have been around for so long that they are savvy enough to understand this problem and fix it. I’m more worried about end-users who have accidentally opted in to this over the years.

HJS: One aspect to consider, does the web really need these? If we try not to do (1) and try not to do (3), what remains in between? There are two status quos, one for Firefox and Chrome in which these are aliases for the city-based identifiers, and one for Safari where they are rejected. Given that they are rejected in Safari, that strongly suggests that we might be able to not have these on the web. Conversely, it might be possible to continue treating these as aliases like Firefox and Chrome. And who sets their system time zone by editing a text file? Would it be feasible to just consider these aliases at the operating system level, regardless of what we do in ECMAScript?

JGT: The ECMAScript spec currently works using an alias mapping process. E.g., "EST" maps to "America/New_York". So what you are describing does exist, but it's our responsibility, not the OS's.

SFC: As of now, the EST-to-EDT (or whatever it’s called) is still the same behavior as “America/New York”. It’s not a problem, yet. It’s only a problem when there is no city remaining that uses that time zone. If it becomes an issue, we could consider what to call the time zone in a time-zone picker (e.g. “Legacy New York”). I think for now, treating them as aliases is fine. I also like the idea of seeing whether it is web-compatible to simply reject them. It’s new information that Safari is behaving in that way, and I do think it’s within the script of ECMAScript to restrict the time zones exposed to the web. I don’t think it’s unprecedented to diverge slightly from IANA. I think if ECMA wants to say “we reject these,” that’s totally within the scope.

JGT: In the current ECMAScript spec, there is a nice clause saying that every value in TZDB is recognized and mapped to something. I think there is value in that. It's helpful to be able to accept everything, even if browsers decide to mask it from users. I'd prefer to retain that invariant (that we accept all IDs) if we can.

Robert: Some rationale for why we do it that way in CLDR, is that we prefer to follow TZDB. (This includes pre-1970’s data.) If some app gets its data from TZDB itself and uses CLDR, that should match. I'd prefer not to have these zones but I consider it more important to be stable. I think it's unlikely that TZDB or CLDR will undo the unlinking for that reason.

JGT: That matches my understanding. If we do anything, it will have to be on the ECMAscript side.

EAO: I support a change to the spec saying that EST5EDT etc are not allowed as canonical IDs. We can leave it up to the implementations whether they wish to accept them as aliases or not. That would allow the current web reality to continue. Second, what's your position on the SystemV-prefixed identifiers, which are also enumerated by Intl.supportedValuesOf?

Robert: The funny thing there is that this all ICU code running in the background, right? They are exposed in ICU because they used to be in TZDB, but they shouldn’t be in the web, either because they are old legacy zones.

JGT: I think they’re accepted in Chrome, but I don’t know if they are enumerated by Chrome.

EAO: I don't remember if we tested enumeration in Chrome. They are enumerated in Node.js.

JGT: Testing now, as of Node.js 26.x they aren't

HJS: In general I prefer well-defined behavior on the Web. I'd prefer to spec either how Safari does or how Chrome/Firefox do. My current preference would be to try to reject them like Safari does. There was this concern about whether the US changes its time zones and then there's nothing for these to alias to. What would be the legitimate use case for a system to remain on this time zone?

Robert: I think during a transition, it might be useful, because maybe some communities decide they want to keep the old behavior.

JGT: I strongly agree with HJS that the more specific we can be in the standard, the less cross-browser variation, the better. I'd prefer retaining them as aliases rather than rejecting them as Safari does. That seems like the better choice considering that ECMAScript runs elsewhere than browsers too. As for existing use cases, there are plenty of alternatives under the Etc/ zones.

Robert: Look what happened in Canada: everyone is doing their own thing, and it’s a huge mess. If you link this to New York, and Georgia stays the same, then the link will be wrong. I would strongly advise against linking them to cities. That’s just going to push the issue to whenever the US stops doing DST.

JGT: I agree that there are arguments on both sides, and there’s no obvious right answer.

HJS: It seems to me that we shouldn’t link this to specific cities. If New York changes, and Ontario legislates based on New York, and then Washington DC does things on a separate time than New York… I would be astonished if all the cities are organized enough to do this at the same time (the Canadian provinces clearly are not). Tht would mean the alias would need to be updated over time. We couldn’t get the information from TZDB which is unfortunate because that’s where it’s supposed to come from . Say NY changes and the alias changes to DC, and then DC changes and the alias changes to Miami–that’s a problem. People could have the same problem for some other timezone-political reason, so it’s within the scope of “what sort of problems arise when time zone changes in some way?” If we don’t want to maintain too much of that in a web-facing way, then it would be the safest to say on the web, “we reject like Safari”, but then on POSIX systems the time zone could be set to one of these, and the browser needs to do something–but something on a low layer. Some alias behavior would need to happen there.

JGT: I believe that's the current behaviour of ECMAScript. When we get the TZDB ID from the operating system, it gets aliased to what we believe is the closest one based on CLDR today. As long as the TZDB ID is valid, it will get aliased to something. We never strand the user. That's why I'm concerned about rejecting it.

Robert: There are two different points: when you read the operating system ID and when you get it as input to DateTimeFormat. You could reject one but not the other.

JGT: Correct.

SFC: I think that it’s not too bad if the aliases jump around from city to city. I think those updates should be pushed in the same push. It would be very bad if they were in different releases,but I believe they’re synchronized in browsers. I hear what Henry said about storing old IDs, but that’s how every time zone works. The only actual problem I see with supporting these zones as canonical zones is the risk with how they behave in pickers and how they’re rendered in pickers. CLDR can call them whatever it wants, like “legacy Eastern Time” and “legacy Central Time”. When you search for them in your enumeration, that’s what you see. The only real risk is when someone types in “EST” or “CST”, it will match by the IANA ID which is not great. But we have a way to localize the name–we support time zone display names, so any well-crafted app should show the users “legacy (something)”/

Robert: CLDR doesn't have by-name IDs for these, they just format as the offset. I don't consider these to be too different from Etc/GMT-5. That is also not a zone that a user should ever pick. They should pick the city. You could make the case that all of these non-location zones should be filtered out of pickers.

EAO: There is some indication of these string identifiers being used, but only in the context of the system time. We do not have any evidence (currently) of these time zone identifiers being used on the web (see how Safari fails on them). That state of affairs, I think that would be okay for us to claim it is unsupported as long as something sensible happens when the system time is set to one of these. That would be an implementation concern.

HJS: I think we can't rely on these having display names that have "Legacy" in them. We'd have to convince CLDR to make that change, and then trust that it propagates correctly through localizations so that it's UI list-friendly.

JGT: I think that’s right. I‘ve done a bunch of usability research, though not specifically on time zones: watching people "across the glass”. Users (especially non-technical users) have tunnel vision. They pick what sounds right–they might not read all the words. I believe the CLDR translations we have today, they are going to call them the long time zone name. That make sit even worse because they would show up in the UI. I agree that the ideal would be to make them an alias.

EAO: What is the expected time scale of this change landing in ICU?

Robert: We have a new major version of CLDR and ICU coming out in 2 weeks.

JGT: I just tested Chrome; it’s not in production Chrome, yet. I assume it will be available whenever Chrome picks up the next ICU.

Robert: It may be even sooner because I believe Chrome does out-of-band updates for ICU

JGT: Proposal: Make a change to ECMA-402 to call out that these particular zones are aliases to the zones that they aliased to from 2024-2026, and no other changes.

SFC: Although it’s not a problem now, it may become a problem, then we would have to figure it out again. I think the problem is likely enough that we should not just kick the can down the road. I don’t necessarily want to “bless” these zones; I kind of want to remove them. If one of the major three browsers is not supporting them right now, keeping that status quo seems acceptable. I prefer to explore something more along the lines of what Justin presented as “number 3”. Maybe it could take an option, or it could take “time zone, comprehensive”. If you don’t have that, you just get the “recommended” primary zone (or similar).

JGT: If we were to do that, I'd almost recommend doing (2) right now, since it's easy and fast, and then have a longer discussions about adding options. There are use cases for different kinds of enumerations, it's true. Caching vs. UI pickers.

SFC: I think we can do option number two now except allow Safari to just not support them. Option two, now, is keep the status quo, ignore the IANA change, and then explore a long-term solution. Is Safari spec-compliant, given that they don’t support the zone name? I thought the spec said we have to have all the IANA names. We might want to update the spec to allow Safari to be compliant (because I like Safari’s behavior). We might want to allow Firefox and Chrome to allow the 2024-2026 behavior; if that needs a spec change, then we should make that change.

JGT: I'm fine if engines choose to deviate from the spec, but I'd rather that than encoding browser differences in the spec.

EAO: Proposal: Ban these IDs as canonical identifiers, which allows the status quo in all 3 major browsers but will prevent these identifiers showing up going forward. Then we can decide what further steps to take.

SFC: Yes. I think there’s a way to write the spec that is clean and doesn’t come off as reifying non-compliant behavior.

JGT: I will make a PR that captures what EAO and SFC just said. 

EAO: Sounds good! Note that ECMA402 changes need to go through TG1. If we can get that proposal in and get alignment on what we want, we can possibly have movement soon–this is a change browsers can make without breaking the current spec.

SFC: I don't think we need to block on process. We should just make sure that Chrome and Firefox continue to align in the meantime.

### Amount Issue #139: Duration / time units in Amount — Use Intl.DurationFormat?

https://github.com/tc39/proposal-amount/issues/139

SFC: Intl Sequence Units does not support time units. This only impacts Intl.NumberFormat, not Amount. That leaves the door open for Amount to support time units using Intl.DurationFormat. The open question is whether to do this.

EAO: Yes, we should. Having these units not be localizable would be very, very weird. The complication is that the options bag can now be either a NumberFormat options bag or DurationFormat options bag. 

SFC: Is it really that bad for Amount to throw on formatting a time sequence unit?

EAO: I haven't checked, but the MediaLength value has a preferred output of minutes-and-seconds, so it can lead to weirdness we don't want.

SFC: Is there a reason why MediaLength doesn't use Temporal.Duration? Why an Amount?

EAO: As currently specified, we are solely relying on the CLDR unit text format as to what is allowable. I think a user would have a reasonable expectation that this should work. If we can't make it work through Intl.NumberFormat, we should make it work through Intl.DurationFormat, and the cost of that is the UX of the options bag.

SFC: I don't love the options bag being different shapes. How do we feel about making Amount.toLocaleString options bag being a very small subset of what both formatters support?

EAO: I would not prefer that. That's not how other toLocaleString methods work. We could have special handling for a few options, but in general as a user I'd expect it to just work the same way that other toLocaleString methods work. This seems like the least worst option.

SFC: The problem is that Amount already wouldn't line up with what DurationFormat does. DurationFormat supports month-and-day which is not in the CLDR unit text format. We spent a lot of time deciding that DurationFormat was really a different thing from NumberFormat, DateTimeFormat, and RelativeTimeFormat, and I don't want to undo that.

EAO: I'm not aware of any changes proposed to the NumberFormat options bag.

SFC: What do you think about not supporting month-and-day?

EAO: Those already don't work for Amount conversions, so that's OK.

SFC: The only one already related to unit formatting is unitWidth (or unitDisplay) that lets you pick between long, medium, short. And then there are standard options such as localeMatcher.

EAO: So what you would like is for Amount.toLocaleString, on an Amount that has minute-and-second units, you would go through DurationFormat, and end up with the same representation that I wish you could just feed into NumberFormat?

SFC: It could also be the case that we plumb them through NumberFormat but only allow that code path to be called through toLocaleString. My arguments against this in plenary still stand. It's just you, me, and Richard who have opinions on this, so it's hard to get anyone else to have an opinion.

RGN: EAO and I have the same opinion, and you're right that there's little other input than the 3 of us.

SFC: It's already the case that we support formatting only a few of the vast number of things you could put into an Amount unit. I think keeping time out of that list is not that bad. I don't find the MediaDuration usage compelling, I think it's OK to not support that. This is not a data-driven exception, because most of the time if your duration units are going to be multi-field, they'll be multi-field right off the bat. It's unlikely that a user will randomly be testing only minutes locally, and then crash in production with hours-and-minutes.

EAO: I'm finding it surprising that sequence units are considered to be second-class in this space. Single units format, sequence units don't? I don't understand what aspect is driving this. It's fine if NumberFormat can't format these specific Amounts, but we do have DurationFormat right there. Why should Amount not use DurationFormat for formatting Amounts that are in the shape accepted by DurationFormat?

SFC: The same reason to support time units is that Amount should just work. It would be weird for Amount to support any unit but time units, because you'd have "if time unit do this, else do that." Now the same thing is happening with formatting. If we have the polymorphic options bag, you have to have an "if time unit do this".

EAO: This is why my preference is that NumberFormat supports them. It would reduce the number of workarounds needed. We bring a whole other class of concerns onto the table if we don't support this.

SFC: Maybe we want to make it easy to convert from Amount to Temporal.Duration? Amount.p.toDuration, which throws an exception if the units are not duration units?

EAO: File that issue! Or maybe Temporal.Duration.from should accept an Amount?

RGN: Not unreasonable, I wonder how big the shape mismatch is.

#### Conclusion

SFC to file an issue about conversion from Amount to Temporal.Duration.

### Unit Protocol Issue #6: Should we coerce the value field?

SFC: Currently, ToIntlMathematicalValue does a lot of stuff, including "weird stuff" like converting numbers to strings and back again. A lot of this weird stuff is justified.
